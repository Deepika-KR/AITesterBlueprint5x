VWO-49: Add Passkey and SSO Login Options

Test plan for authentication options on the VWO login page

Issue: VWO-49 Project: VWO Project Epic: Authentication Enhancements Prepared: 28 October 2026 Issue status: To Do (ticket export) Plan status: Draft — pending human review

Review status: This is a proposed test plan, not an approved or final artifact. Ticket content and historical comments are taken from the supplied VWO-49 export. Questions and unconfirmed details are kept open rather than assumed.

1. Objective and Company Context

Verify that users can start and complete VWO login using the newly presented Single Sign-On (SSO) and passkey options, receive safe and understandable failure guidance, and use the options on supported configurations without exposing sensitive authentication data.

Supplied organization context

The company notes describe VWO as a Bingify product at vwo.com, focused on A/B testing for websites, with approximately 5,000 employees. This context is supplied in the skill materials; it is not independently verified.

Test objective

Assess the new login entry points and the SSO/WebAuthn authentication journeys in scope, plus security, compatibility, accessibility, and responsive behavior directly related to these options.

2. Ticket Summary and Scope

User story: As a user, log in using either Passkey or SSO to access an account more securely and conveniently without relying solely on email/password authentication.

Ticket metadata: Story; VWO Project; status To Do; priority appears as Medium in the issue header and High in the description; no components, fix version, sprint, or assignee are supplied. Epic link is Authentication Enhancements.

In scope

  • Visibility and placement of “Sign in using SSO” and “Sign in with Passkey” beneath “Sign in with Google”.
  • Configured SSO success, failure, user feedback, and dashboard redirect.
  • Registered passkey success, failure, no-passkey fallback/guidance, and unsupported browser/device handling.
  • Supported browser/device and configured identity-provider compatibility; secure OAuth/SAML/WebAuthn behavior.
  • Responsive and accessible presentation; sensitive-data exposure checks in UI and network logs.

Out of scope / conditional

  • Passkey registration, explicitly covered by another story.
  • SSO provider configuration, explicitly out of scope. Use only configured providers and test-environment setup.
  • Testing provider administration or the broader VWO product beyond login and dashboard handoff.

Existing email/password and Google login are included only as regression checks where they share the login page or could be affected by placement.

Acceptance criteria reference

RefTicket requirement
AC-1Both named buttons are visible on login, below “Sign in with Google”.
AC-2Valid SSO credentials authenticate the user and redirect to the dashboard; invalid credentials produce an appropriate error.
AC-3A verified registered passkey logs the user in and redirects to the dashboard; no passkey produces fallback or guidance.
AC-4Appropriate errors are displayed for failed SSO, failed passkey authentication, and unsupported browser/device for passkeys.
AC-5Passkey works on supported browsers/devices; SSO works across all configured identity providers.
AC-6Authentication follows secure OAuth/SAML/WebAuthn protocols; sensitive data is not exposed in UI or network logs.

6. Strategy, Entry/Exit Criteria, and Deliverables

Approach

  1. Review this draft with product, QA, engineering, and identity-provider owners; resolve blocking questions and approve scenario priorities.
  2. Confirm environment, build, access, feature state, test identities, configured providers, and supported-device matrix; run smoke checks.
  3. Exercise the UI and core success paths first, followed by failures, security/privacy checks, compatibility, accessibility, responsive behavior, and regression.
  4. Record results and defects in the project’s approved tracker; retest fixes and run focused regression. Report blocked tests with a named dependency, not as pass/fail.

Entry criteria

  • Plan/scenarios reviewed; critical ambiguities resolved or explicitly accepted by the owner.
  • Approved non-production build and environment reachable; identity-provider test setup and test accounts ready.
  • Supported platform matrix, access, and execution evidence process agreed.

Exit criteria (proposed)

  • All approved P0 scenarios executed; other planned coverage completed or blockers documented and accepted.
  • No open critical/high defects for agreed scope, unless a named stakeholder accepts documented risk.
  • Security, compatibility, accessibility, defect, and test-result summaries shared; release/sign-off decision recorded by owner.

Numerical pass-rate and defect thresholds are not stated in the ticket and require owner approval.

Deliverables and defect handling

  • Approved plan and resolved requirement questions; prioritized scenario/test-case traceability to AC-1–AC-6.
  • Execution results with environment/build, test matrix, evidence references, defects, retests, blockers, and residual risks.
  • Report reproducible defects in JIRA (or the approved project tracker) with sanitized reproduction details, expected/actual behavior, environment, severity, and priority. Do not include authentication secrets.
